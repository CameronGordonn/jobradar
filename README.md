# jobradar

[![tests](https://github.com/CameronGordonn/jobradar/actions/workflows/tests.yml/badge.svg)](https://github.com/CameronGordonn/jobradar/actions/workflows/tests.yml)
[![daily pipeline](https://github.com/CameronGordonn/jobradar/actions/workflows/daily.yml/badge.svg)](https://github.com/CameronGordonn/jobradar/actions/workflows/daily.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

jobradar pulls job postings from USAJOBS and 48 company boards on Greenhouse, Lever and Ashby, and does two things with them:

1. **Ranks them for one person.** Hard filters, a cheap recall stage and a Claude rerank against a written rubric turn about 5,400 postings a day into a short daily list. It never applies or sends anything.
2. **Keeps a public warehouse of the postings.** A scheduled GitHub Actions job loads them into DuckDB, models them with dbt, tests them, and publishes aggregate charts.

**Evaluation:** on 200 hand-labeled postings (12 labeled apply), the Claude rerank reaches precision@10 of 0.61 to 0.73 against 0.20 for TF-IDF, and its gain over TF-IDF has a 95% bootstrap CI above zero for all three models tried. Haiku 4.5, Haiku 5.5 and Sonnet 5.5 can't be told apart at this sample size, so production runs the cheapest, Haiku 5.5 ($0.04 per daily run). The weak point is recall: ranked over the whole pool, TF-IDF puts 10 of the 12 apply postings below the 40 that reach Claude. Two thirds of the labeled postings come from five large employers, and self-agreement (40 postings relabeled a week later) is still pending. Full results in [results/eval_summary.md](results/eval_summary.md), regenerated by one command (`python -m jobradar.cli eval --report`).

**Dashboard:** [camerongordonn.github.io/jobradar](https://camerongordonn.github.io/jobradar/) (rebuilt daily by the scheduled job; live after its first run with Pages enabled).

## Architecture

```
                     sources.yaml (public)                         config.yaml + rubric + resumes (personal, gitignored)
                            |                                                       |
USAJOBS  Greenhouse  Lever  Ashby                                                   |
   \         |         |    /                                                       |
    raw_<source> tables in DuckDB (payload as returned, upserted on source job id)  |
        |                                         |                                 |
        |  public warehouse (GitHub Actions)      |  personal ranking (local, daily)|
        v                                         v                                 v
  quality checks -> dbt: staging -> int_jobs -> marts      stage 0: hard filters -> stage 1: TF-IDF recall
                        (tests, freshness,     |           -> stage 2: Claude rerank (top 40) -> digest
                         unit test)            |
                     dedupe (embeddings) ------+
                                               v
                                   dashboard on GitHub Pages
```

## Ranking pipeline

| Stage | What it does |
|---|---|
| 0. Hard filters | Title words (senior, staff, intern...), location allow and block lists, the source's country field, clearance wording, minimum years of experience, USAJOBS hiring path and GS grade. Biased toward keeping postings. |
| 1. Recall | TF-IDF (words and word pairs) cosine against each resume variant, best match kept. The top 40 unscored postings go on. |
| 2. Rerank | Claude reads the posting against the rubric and resumes and returns a 0-10 fit score, a recommendation, gaps and an opening line through a tool call. One posting per call (pointwise). The rubric and resumes are a cached system prompt. |
| Digest | The top 10 new postings above the fit threshold, as markdown. |

## Evaluation

The labels are blind and drawn once, so the metrics measure the pipeline rather than flatter it:

- **Set a**: 200 postings that passed stage 0, 20 from each stage 1 recall decile. The deciles are equal-sized, so set a is close to a uniform sample of everything stage 0 keeps.
- **Set b**: 30 postings stage 0 dropped, stratified by rule, to find filter false negatives.
- **Set c**: 40 postings from set a, relabeled at least 7 days after set a is done. Agreement with my own earlier labels is the ceiling for any ranker.

The labeling screen shows title, company, location, an excerpt and the link, and hides every score, rank and filter reason. Labels are apply, maybe or no.

Rankers compared on the same labeled postings: TF-IDF (stage 1 as it ran), local embeddings (bge-small-en-v1.5, chosen before seeing results for its 512-token window; all-MiniLM-L6-v2 for reference), and the Claude rerank with Haiku 4.5, Haiku 5.5 and Sonnet 5.5. Metrics: ROC AUC, average precision, precision@10 and @20, with percentile bootstrap CIs over 2,000 resamples of postings, plus paired differences against TF-IDF. The report also covers cost per daily run from measured token counts, score stability when the same 50 postings are scored twice, the stage 0 and top-k audits, and self-agreement.

```bash
python -m jobradar.cli label-sample                 # once
python -m jobradar.cli label --set a,b              # blind labeling
python -m jobradar.cli eval-embed                   # local embedding scores (pip install -r requirements-eval.txt)
python -m jobradar.cli eval-score --model claude-haiku-4-5-20251001 --run 1          # prints a cost estimate
python -m jobradar.cli eval-score --model claude-haiku-4-5-20251001 --run 1 --yes    # spends, within the eval budget
python -m jobradar.cli eval --report                # results/eval_summary.md, eval_metrics.json, precision_at_k.png
```

Claude scoring goes through the Batch API at half price, and `eval-score` refuses to pass a $5 eval budget unless told to. Labels, resumes and the rubric stay out of the repository, and anything that pairs a posting with a label is written to a gitignored file; a test checks that no labeled posting title reaches `results/`.

## Data pipeline

`python -m jobradar.pipeline` needs only `sources.yaml`, so it runs unattended.

- **Ingest**: one raw table per source with the API payload, `first_ingested_at` and `ingested_at`. Loads upsert on the source job id, so a rerun never adds rows. Every run logs rows fetched and new per source to `ingest_runs`.
- **dbt** (`warehouse/`):
  - staging: one model per source, normalized to a shared schema (title, company, location, URL, workplace type, dates, salary with currency and interval).
  - intermediate: `int_jobs` with a cleaned and normalized title, role family (regex rules in a seed), remote flag, posted date, yearly salary, open status and a dedupe cluster.
  - snapshot: `snap_postings` keeps every version of each posting (title, location, salary, remote and open status), since the raw tables keep only the latest payload.
  - marts: open postings with near-duplicates collapsed, daily postings per source, weekly postings by role family and company, per-run source health, closed postings with days listed, and per-posting edit counts from the snapshot.
  - tests: unique and not_null keys, accepted_values on every enum, relationships from the marts and clusters back to `int_jobs`, singular tests, unit tests on `int_jobs` and the lifecycle mart, and source freshness (warn at 30 hours, error at 54). A pytest builds twice around a run with known edits and checks the snapshot counts exactly those.
  - docs: `dbt docs generate --static` is published next to the dashboard at `/dbt/` (models, columns, tests, lineage).
- **Data quality**: each run compares every source's row count with the median of its previous 7 runs and flags a drop below half, which usually means an API change. It also flags each configured board that loaded nothing, which a source's total hides (a company that moved to another job board). Flags go to `quality_checks`, show as warnings on the Actions run, open (or comment on) a GitHub issue labeled `data-quality`, and source-level flags appear on the dashboard.
- **Near-duplicates**: "ML Engineer" and "Machine Learning Engineer" at the same company are the same job. Postings are embedded as "title | company | location" and compared within a company. The threshold comes from 50 hand-marked pairs drawn across the similarity range (pending; until then only exact matches collapse).
- **Schedule** (`.github/workflows/daily.yml`, daily at 14:17 UTC): restore the warehouse, ingest, quality checks and alerts, freshness, dbt build, dedupe, marts, dashboard and dbt docs to Pages, and a weekly Parquet backup. No Claude calls.
- **CI** (`.github/workflows/tests.yml`, every push): ruff and sqlfluff; pytest; dbt build, freshness, docs and the two-build snapshot test against a committed synthetic fixture (eight daily runs of made-up companies, with a simulated outage the quality monitor must catch).

**Where the warehouse lives between runs.** The DuckDB file (about 16 MB) is uploaded as an Actions artifact at the end of each run and downloaded at the start of the next. Artifacts are kept 90 days, the maximum for a public repository. An Actions cache would be simpler to restore but is evicted after 7 days without use and can go sooner when the repository's 10 GB cache fills, so one quiet week would lose everything. As a second copy, once a week the job publishes the raw tables, run logs, clusters and snapshot history as Parquet in a GitHub Release (about 7 MB). Releases don't expire, so if the artifact is ever gone the next run restores from the latest release and loses at most a week. With neither available, the job stops rather than start over from an empty file. GitHub also pauses scheduled workflows in a public repository after 60 days without commits; re-enabling it brings the chain back from the artifact or the latest release.

## Setup (ranking pipeline)

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env && chmod 600 .env   # ANTHROPIC_API_KEY, USAJOBS_API_KEY, USAJOBS_EMAIL
cp config.example.yaml config.yaml       # personal filters and resume list (gitignored)
cp rubric.example.md rubric.md           # fill in the candidate section (gitignored)
python -m jobradar.cli run               # ingest -> score -> digest; writes digests/YYYY-MM-DD.md
```

Resumes go in `resumes/` as plain text. Boards go in `sources.yaml`; check a token first with `python -m jobradar.cli probe greenhouse|lever|ashby <token>`. `scripts/daily_run.sh` runs the pipeline from cron or Windows Task Scheduler (through WSL), appends to `data/run.log`, refuses to overlap a running job, and exits non-zero if scoring fails. Claude spend is capped at `recall.top_k` calls per run.

To build the warehouse locally: `pip install -r requirements-pipeline.txt`, then `python -m jobradar.pipeline ingest`, `cd warehouse && dbt build --profiles-dir .`, and `python -m jobradar.pipeline dashboard`.

## Tests

`python -m pytest -q` runs offline on recorded and synthetic fixtures: adapters, filters, idempotent raw loads, the SQLite and key migrations, one Claude call per duplicate group, label sampling and blindness, the relabel lock, metrics (checked against brute force over tie orders), the eval report's privacy, the quality monitor, dedupe, Parquet backup and restore, and the dashboard export. With dbt installed it also builds the warehouse twice to test the snapshot. `cd warehouse && dbt build` runs the warehouse tests; `ruff check .` and `sqlfluff lint models tests` (in `warehouse/`) run the linters.

## Known limitations

- The dashboard covers the queries in `sources.yaml` and 24 hand-picked boards, not the job market.
- "Postings by week first published" only sees postings that were still open at the first ingest, so earlier weeks are undercounted until the pipeline has run for a while. "Days listed" has the opposite bias early on: long-listed postings are more likely to be caught, so early medians run high.
- USAJOBS searches return the last 14 days of announcements, and USAJOBS dates have no time zone (US Eastern, stored as given).
- Role families come from title rules. About 8% of open postings match no rule and count as "other".
- TF-IDF weights shift as the corpus grows, so recall scores aren't comparable across weeks. The eval uses scores frozen when the label sets were drawn.
- Both embedding models truncate long postings (512 and 256 tokens).
- One labeler. The eval measures how well the rankers match one person's judgment, bounded by that person's consistency.
